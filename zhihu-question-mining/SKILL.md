# 知乎提问挖掘（Zhihu Question Mining）

把一段**口语稿、录音转写、随笔笔记或长文档**，拆成**多个可以单独发布的知乎提问**。

每个提问交付两样东西：

1. **标题**——一句话，精准、有力、有讨论空间
2. **问题描述**——保留本人的说话方式，把困惑讲清楚，但不提前下结论

**它不是什么**：把稿子改写成文章；把一个大问题包装得漂亮；替你想出你没想过的问题；替你在知乎提问框里自动发布。

本文件是可执行规范。**核心方法见 `references/topic-splitting.md`**；标题规则见 `references/title-craft.md`；描述风格见 `references/description-style.md`；真实案例见 `references/worked-example.md`。

---

## 0. 四条不可违背的元原则

| 原则 | 含义 | 防止的失败模式 |
|---|---|---|
| **一个提问 = 一个核心矛盾** | 不是一段录音的摘要，是一个能独立成立的冲突 | 把好几件事塞成一个"大问题"（FM-4） |
| **保住说话的那个人** | 第一人称、口语、具体例子、真实困惑，一个都不能丢 | 整理感太重、文绉绉、像专栏文章（FM-1、FM-6） |
| **具体对象前置** | 标题用产品名/作品名/真实场景切入，抽象留给描述 | 标题太泛、像行业报告题目（FM-2、FM-3） |
| **不写成预设答案** | 困惑要保留开放性，不要把自己的判断当前提 | 像在自问自答，吸引不到真正懂的人（FM-7） |

## 一、先理解稿子，不要马上写

### 1.1 话题单元切分

**这一步做不好，后面全是把一篇长文切成几段。**

口语稿的特点是：**发散、重复、话题来回跳、没有小标题**。不能按段落切，要按**矛盾**切。完整方法见 `references/topic-splitting.md`。

**契约**：输入一份稿子，输出——话题单元表（含每个单元的触发场景与核心矛盾）、合并/拆分判定记录、粒度检查结果。

**六步摘要**：

| 步 | 做什么 |
|---|---|
| **A 标记** | 通读全篇，标出五类东西：**具体场景/不爽**（触发点）、**已有的疑问句**、**用户判断**、**事实与引用**、**重复与岔路** |
| **B 切单元** | 按**场景切换**和**矛盾对象切换**切分。同一个矛盾的不同段落 → 合并 |
| **C 提炼矛盾** | 每个单元写成一句：**「我看到 A，但实际是 B」**或**「大家都说 A，我的体验却是 B」**。写不出这个句式 → 它还不是一个话题 |
| **D 定粒度** | 跑**过度拆分检测**与**过度合并检测**（见 1.3） |
| **E 排优先级** | 按「具体程度 × 矛盾强度」排序，不按稿子顺序 |
| **F 产出** | 话题单元表 + 判定记录 |

### 1.2 提炼核心矛盾

每个话题单元必须能填出这个句子：

> **我看到 / 我遇到的是 ______，但按理说 / 大家都说应该是 ______。**

例：

- 「微信打电话能直接用蓝牙耳机，**但** AI 对话反而不行。」
- 「组织追求去个人化，**但** 优秀作品又高度依赖个人。」
- 「我的体验是刚起床特别难做决定，**但** 有些人遇到新问题就是能很快反应过来。」

**填不出这个句式的话题，不要写。** 它多半只是资料、感慨或背景，不是一个能独立成立的提问。

### 1.3 决定拆到什么粒度

两个方向都会错，都要防：

| 检测 | 症状 | 修正 |
|---|---|---|
| **过度合并** | 一个提问里有两个独立矛盾（描述里出现「另外」「还有一个问题」） | 拆开成两个提问 |
| **过度拆分** | 拆出来的问题没有具体场景支撑、或描述不足三句、或两个问题共享同一个触发场景 | **合回去** |

**重要**：如果用户已经认可了一套话题划分，**不要继续往下拆**。用户说「原来分出的 7 点挺好的，内容再润色就行」时，改动范围就只是标题和描述的文字——不要重新划分话题。这是最常见的一种越界。

## 二、标题：从具体痛点切进去

**一句话原则**：标题要让**具体的东西**先出场，把抽象留给描述。

### 2.1 五条判据

1. **具体对象优先**——产品名、作品名、真实场景，比抽象概念更抓人
2. **反差结构**——「A 能，B 为什么不能」「都这么厉害了，为什么还这么麻烦」
3. **动词和人话**——「蟑螂到底怎么弄最有效」而不是「如何系统治理蟑螂」
4. **允许一点情绪**——「难道人类到现在还没一套靠谱办法吗？」是好的
5. **一行以内，不标题党**——不夸张、不制造虚假悬念、不用「浅析/探析/成因」

### 2.2 三条真实反例（都是被用户退回的原话）

| ✗ 被退回 | 原因 |
|---|---|
| 「AI 到底怎样才能真正融入日常生活，而不是有问题时才拿手机出来问？」 | **太泛，像行业报告题目** |
| 「为什么很多作品一旦失去"灵魂人物"，整个味道就变了？」 | **抽象层级提得太早**，把《凡人》这个最能吸引人点进去的具体对象藏掉了 |
| 「公开分享自己的想法，会让个人受益，还是在主动放弃"信息差"？」 | 用「信息差」这种词，**不像普通人会这么问** |

### 2.3 同一话题的三次修改（真实记录）

| 版本 | 标题 | 问题 |
|---|---|---|
| 一稿 | 为什么 AI 助手不能像微信电话一样通过蓝牙耳机直接对话？ | 太长、太书面 |
| 二稿 | 为什么 AI 助手不能像微信电话一样直接用蓝牙耳机对话？ | 仍然没有反差 |
| **定稿** | **为什么微信打电话能直接用蓝牙耳机，AI 对话反而不行？** | 「能 / 反而不行」构成反差，口语 |

完整对照见 `references/title-craft.md`。

## 三、描述：保住说话的那个人

**这是整个任务里最容易做坏的一步。** 口语稿转成书面语时，绝大多数模型会不自觉地"整理"，结果读起来像专栏文章、像行业报告，就是不像一个真人在知乎上提问。

### 3.1 要保留什么

- **第一人称**，从具体场景开始（时间、地点、动作）
- **短句、一句一段**的节奏
- **口语连接词**：我就在想 / 所以我更想问的是 / 就跟…一样 / 这个事我一直挺奇怪的
- **具体名词**：真实的产品名、作品名、地名、数字
- **情绪的痕迹**：有点烦、挺奇怪的、我也想不通
- **困惑的开放性**——保留「可能」「我也说不好」「不知道是不是」

### 3.2 只做三件事

1. **去重复**——同一句话说了三遍，留一遍
2. **理顺逻辑**——把来回跳的顺序摆正
3. **让别人能快速看懂你在问什么**

### 3.3 不要做（每一条都对应一次真实退回）

- ❌ **不要"整理"**：不要加小标题、不要编号分点、不要提炼"核心观点"、不要总结
- ❌ **不要拔高**：不要把「刚起床脑子没开机」写成「晨间认知功能激活滞后」
- ❌ **不要替用户下结论**：用户说「我怀疑」，不要写成「事实证明」
- ❌ **不要写成预设答案**：把自己的判断写成提问的前提，会让真正懂的人不想答
- ❌ **不要用书面套语**：进行、从而、基于、综上所述、值得注意的是

> **判断标准**：把描述念出来，像不像这个人**真的会在知乎上这么问**？不像，就是整理感太重了。

### 3.4 结尾格式

描述的最后，落到一个**明确的疑问句**（可加粗），后面可以跟 1–3 个追问。

```
所以我更想问的是：

**这种快速判断、快速解决问题的能力，到底能不能练？**

如果能练，平时应该怎么练？
```

完整 before/after 见 `references/description-style.md`。

## 四、交付格式

默认输出：

```
### 1. <标题>

<问题描述，第一人称，多段>

---

### 2. <标题>

<问题描述>

---
```

**规则**：

- 一个问题一个编号，之间用 `---` 分隔，便于单独复制发布
- 标题**不加**序号以外的任何前缀（不写「问题一」「Q1」）
- 描述里**不要**出现「以上是我的一些想法」这类收尾套话——它是要发出去的提问
- 每个提问下面**不要**附「为什么这么问」的说明（除非用户明确要）
- 交付后单独列一段**极简说明**：列出话题划分依据、合并了哪些、拆了哪些。**这段不是发布内容**

---

## 五、交付前自检

逐项回答「是/否 + 证据」：

1. **一个矛盾**——每个提问是否只有一个核心矛盾？描述里有没有出现「另外」「还有一个问题」？
2. **填得出句式**——每个提问是否填得出「我看到 A，但应该是 B」？
3. **具体对象**——标题里有没有具体的东西（产品名/作品名/场景）？还是全是抽象概念？
4. **念得出来**——把每段描述念一遍，像不像这个人真的会在知乎上这么问？
5. **第一人称还在**——有没有哪一段变成了第三人称的客观陈述？
6. **没替用户下结论**——有没有把「我怀疑」写成「事实是」？
7. **开放性**——有没有哪个提问其实已经把答案写好了，变成自问自答？
8. **没过度拆分**——拆出来的每个问题都有具体场景支撑吗？有没有描述不足三句的？
9. **没过度合并**——有没有哪个提问其实装了两件事？
10. **能直接发**——单独把某一条复制出来，能不能直接贴进知乎提问框？有没有残留「以下」「如上」之类依赖上下文的词？

任何一项失败，先改再交付。

## 六、失败模式目录

**全部来自真实的六轮修改记录**，不是想象的。

| 编号 | 失败模式 | 真实证据 | 修正 |
|---|---|---|---|
| **FM-1** | **整理感太重，像专栏文章** | 用户原话：「问题还是不行，不够接地气，感觉太文绉绉的」；「还是'整理感'太重，像专栏文章，不像普通人真的会在知乎上这么问」 | 去掉小标题、分点、总结；短句；口语连接词；念出来检查 |
| **FM-2** | **标题太泛，像行业报告题目** | 用户退回：「AI 到底怎样才能真正融入日常生活…有点奇怪」；改稿者自述「第 4 个太泛，像行业报告题目」 | 从具体痛点切入；加反差结构 |
| **FM-3** | **抽象层级提得太早，藏掉最有吸引力的具体对象** | 改稿者自述：「第 7 个抽象层级提得太早，把《凡人》这个最能吸引人点进去的具体对象藏掉了」 | 具体对象前置到标题，抽象留给描述 |
| **FM-4** | **把多个矛盾塞成一个"大问题"** | 用户原话：「你是不是忘了，我要的是准备发表到知乎提问里面，拆分多个问题」；改稿者自述「我把第 4、7 两块又写成了'一篇大问题'」 | 一个提问一个矛盾；描述出现「另外」就拆 |
| **FM-5** | **过度拆分，丢了已经认可的划分** | 用户原话：「不是，原来分出 7 点的文档挺好的，内容再润色就行」 | 用户认可划分后，改动范围只限文字；不重新划分话题 |
| **FM-6** | **抹掉个人语言风格** | 用户原话：「问题描述内容，要尽量贴合保留个人的语言风格」；改稿者自述「上一版确实有点'整理得太标准'，把你原本那种一边想、一边追问、一边举例的个人感削弱了」 | 保留第一人称、口语、具体例子；只做去重复/理顺/让人看懂三件事 |
| **FM-7** | **把自己的观点写成预设答案** | 首版原则：「问题本身清楚，但没有把自己的观点写成预设答案，这样更容易吸引真正懂这个领域的人回答」 | 保留困惑的开放性，不要把判断当前提 |

## 七、本 skill 的更新方式

本 skill 自己也要从后续修改中学习，但**只提炼可迁移的通用规则，不把某一篇稿子的具体修改硬编码进来**。

1. **从具体反馈提炼通用规则**。用户说「这里太文绉绉」，**不能**更新成「不要用'信息差'这个词」；应该提炼成「读者是普通人时，抽象名词要换成他生活里的说法」。
2. **通过通用性测试**：换了主题还成立吗？能适用于口述稿、笔记、长文三种输入吗？能被明确执行吗？
3. **区分三类反馈**：通用规则 / 当前任务规则（这篇稿子要更讽刺）/ 局部修改（这一句换个说法）。只有第一类进长期规则。
4. **旧规则默认保留**，更新前建立清单，逐项确认保留 / 合并 / 改写 / 建议删除。**重写不等于重新发明。**
5. **优先合并，不无限膨胀**；每条规则必须对应一个真实失败模式。
6. **冲突不擅自决定**：方向相反、无法同时满足、要把"建议"升级为"必须"时，列出冲突交给用户。
7. **示例只用于解释规则，不反过来成为模板。** 本文件里的《凡人》、蓝牙耳机、蟑螂都是这一个用户的真实话题，**不是通用题材**。

**规则的优先级**：用户本次明确提出的新规则 > 本 skill 已有规则 > 上游来源。
