# 知乎提问挖掘（Zhihu Question Mining）

一个把**口述稿、录音转写、随笔笔记**整理成**可发布的知乎提问**的 Agent Skill。

输入是一段口语稿（发散、重复、话题来回跳、没有小标题）。输出是**多个能单独发布的提问**，每个包含一句话标题 + 一段问题描述。

> 本仓库对应 `SKILL.md`（执行形态）与 `README.md`（可阅读的形态）。二者来自同一套知识体系：**Skill 是可执行的方法，Blog 是可阅读的方法。**

---

## 它解决什么问题

"帮我把这篇稿子整理成知乎提问"听起来简单，实际会被退回很多次。本 skill 的规则全部提炼自**一次真实的六轮修改**——用户连续退回了 5 版，每次退回都暴露一个失败模式：

| 失败模式 | 用户的原话 |
|---|---|
| **整理感太重，像专栏文章** | 「问题还是不行，不够接地气，感觉太文绉绉的」 |
| **抹掉个人语言风格** | 「问题描述内容，要尽量贴合保留个人的语言风格」 |
| **标题太泛，像行业报告题目** | 「AI 到底怎样才能真正融入日常生活…**有点奇怪**」 |
| **抽象层级提太早，藏掉具体对象** | 「**应该提到《凡人》这个作品吧**，问题提问不够尖锐，不够吸引关注」 |
| **把多个矛盾塞成一个"大问题"** | 「你是不是忘了，我要的是准备发表到知乎提问里面，**拆分多个问题**」 |
| **过度拆分，丢了已认可的划分** | 「**原来分出 7 点的文档挺好的**，内容再润色就行」 |
| **把自己的观点写成预设答案** | （首版原则：不写成预设答案，才吸引得到真正懂的人） |
| **把转写听错的专有名词当事实基础** | 稿里「**ZEV** 第一系统模型」实为 **Jev**——基于一个不存在的名字建了完整话题。更危险的是「**DeepMind**」实为 **DeepSeek**：两个都是真公司，**完全不触发警觉** |
| **拆得太细** | 初划分 **12 个话题**，用户三轮要求合并 **3 次**、要求拆分 **0 次**，最终 **9 个**。其中一次拆分的理由是「原稿已经明确说『另外一方面』」——**把口语连接词当成了话题边界** |
| **合并后丢了标题** | 输出写成 `T5 + T6｜合并描述`，占位标签当标题。用户：「T5 + T6，怎么没有标题？」 |
| **替用户补充他没说过的话** | 描述里被加了「我并不是现在遇到了一个'该选什么专业'的问题，只是好奇」——用户：「没必要这么说明」 |

**注意这两条是相反方向的**：既要拆得够开（一个提问一个矛盾），又不能拆过头（用户认可的划分不许动）。这类任务的一大难处就在这里——**两个方向都会错**。

## 核心主张

### 1. 一个提问 = 一个核心矛盾

不是一段录音的摘要，是一个能独立成立的冲突。每个话题单元必须填得出这个句子：

> **我看到 / 我遇到的是 ______，但按理说 / 大家都说应该是 ______。**

- 「微信打电话能直接用蓝牙耳机，**但** AI 对话反而不行。」
- 「组织追求'去个人化'，**但** 优秀作品又高度依赖具体的个人。」

**填不出这个句式的话题不要写**——它多半只是资料、感慨或背景。

### 2. 标题给具体，描述做升华

这是被退回最多的一条。用户明确指出的两个坏标题：

```
✗ AI 到底怎样才能真正融入日常生活，而不是有问题时才拿手机出来问？
   → 太泛，像行业报告题目

✗ 为什么很多作品一旦失去"灵魂人物"，整个味道就变了？
   → 抽象层级提得太早，把《凡人》这个最能吸引人点进去的具体对象藏掉了
```

**不是「先抽象，再举例」，而是「标题给具体，描述再升华」。**

### 3. 描述要保住说话的那个人

口语稿转书面语时，绝大多数模型会不自觉地"整理"，结果读起来像行业报告。本 skill 只允许做三件事：

**去重复 / 理顺逻辑 / 让别人能快速看懂你在问什么。**

其余一切都是过度加工：不加深小标题、不分点、不提炼"核心观点"、不总结、不拔高、不用书面套语。

同一段原始想法，两种处理（完整对照见 `references/description-style.md`）：

| ✗ 整理感重 | ✓ 接地气 |
|---|---|
| 现在手机打电话、微信语音或视频通话，都可以直接使用蓝牙耳机完成声音输入和输出。 | 这个问题我一直挺奇怪的。现在正常打电话也好，微信语音也好，戴上蓝牙耳机，耳机既能听，也能直接说。 |

判断标准只有一个：**把描述念出来，像不像这个人真的会在知乎上这么问？**

### 4. 用户认可的划分，不许再拆

真实记录：

> 用户：「不是，原来分出 7 点的文档挺好的，内容再润色就行」

此时改动范围**只剩标题和描述的文字**。重新划分话题属于越界——这是这类任务里最常见的一种过度执行。

### 5. 每条规则都对应一次真实退回

不是想象出来的规则清单。每条都能指回会话里的哪一轮、哪一句反馈。

## 安装 / 使用

作为一个 Agent Skill 使用：把 `zhihu-question-mining/` 整个目录放进你的 skills 目录即可（`SKILL.md` 带有 `name` / `description` frontmatter）。

作为提示词使用：直接读取并遵循 `SKILL.md`。

典型触发方式：

```
帮我把这篇稿子整理成知乎提问：<粘贴口述稿>
```

它应该先给出话题单元划分（含每个单元的核心矛盾），再逐个产出标题 + 描述，最后单独列一段极简说明（合并了哪些、拆了哪些）——**那段说明不是发布内容**。

**聊天模式提示词**见仓库根的 [`prompts/zhihu-question-mining.md`](../prompts/zhihu-question-mining.md)。

| 版本 | 内容 |
|---|---|
| **1.1.0** | 第二轮真实调试（4 阶段全流程）后补：**转写核对**（新增 `references/transcript-fidelity.md`——先搜、搜不到就问，不得把未核实的词当事实基础）；**默认存疑则合**（拆分必须有「答案体系不同」支撑，「另外」只看最终描述不看原稿）；**合并后必须补标题**；**不得替用户补充他没说过的话或改写动机**。 |

## 关于案例内容

原始产出含约 **4,100 字符的个人生活内容**（看过的作品、家里的蟑螂、起床状态）。

本仓库**只保留必要摘录**——标题、反馈原话、以及一段对照。**没有收录全部问题描述全文**：把一个人的生活细节完整放进公开仓库，超出了"提炼规则"所需。

完整政策见 `references/worked-example.md` 开头的摘录说明。

> 规则里出现《凡人》、蟑螂、蓝牙耳机，只因为它们**是这一个用户的真实话题**，用作示例。**它们不是通用题材，不要照套。**

## 更新本 skill

三条硬约束：

1. **每条规则必须对应一个真实失败模式**——本 skill 的失败模式全部来自真实退回，新规则也应如此；编不出失败模式的规则不要加。
2. **旧规则默认保留**——重写不等于重新发明。
3. **具体话题不得升格为规则**。用户说「这里太文绉绉」，**不能**更新成「不要用'信息差'这个词」；应提炼成「读者是普通人时，抽象名词要换成他生活里的说法」。

## 还有哪些没有解决

- **话题切分依赖模型对整篇稿子的阅读能力。** 方法给了标记、信号、双向粒度检测，但没有自动化校验；粒度判定目前是**模型自检**。
- **「接地气」没有客观阈值。** 目前靠「念出来像不像人话」和"段落长度是否过于均匀"两个定性判据。
- **没有回归材料。** 原始口述稿含个人内容、不在仓库，所以无法直接跑端到端回归。`worked-example.md` §6 给了检查清单，但需要另找一份口述稿。
- **平台规则会变。** 知乎对标题党、折叠、限流的判定属于平台政策，本 skill 只给了保守边界（不夸张、不虚假悬念），**使用前应重新核实**。
