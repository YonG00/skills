## [1.1.0] — 转写核对；默认存疑则合

**规则来源**：第二轮真实调试会话（4 阶段跑完、9 轮反馈、12 话题收敛为 9）。用户明确点出两个问题：「需要对录音的转写稿，可能有些识别错误，如果觉得不正常可以问我，或者搜索纠正」「还有差异不大的话题可以合并」。

另外从记录里自查出**两个用户没点名但确实发生**的缺陷（FM-9、FM-10）。

### 新增

| 新增 | 位置 | 说明 |
|---|---|---|
| **转写核对**（阶段 1 第一件事） | `references/transcript-fidelity.md`（新文件） | 三类可疑信号（查不到 / **查得到但语境不对** / 同音近音）、处置顺序（**先搜 → 搜不到或不确定就问用户**）、处置动作表、禁止事项、汇报格式 |
| **默认存疑则合** | `topic-splitting.md` D.1、`SKILL.md` §1.4 | 粒度拿不准时**合**而不是拆 |
| **拆分的唯一正当理由：答案体系不同** | 同上 D.2 | 需要不同的人、不同的知识背景来回答 |
| **「另外」的适用对象修正** | 同上 D.3 | 该信号**只看最终描述，不看原稿**——口语稿里「另外」是口头连接词 |
| **合并/拆分后必须重新给标题** | 同上 D.5、`title-craft.md` §5 | 合并产生的是新对象 |
| **不要替我补充没说过的话** | `description-style.md` §3.6 | 判断法：这句话在原稿里找得到依据吗？找不到就删 |
| **不要改写我的动机** | `description-style.md` §3.7 | 动机句照原话保留 |
| **FM-8 / FM-9 / FM-10** | `SKILL.md` §六 | 转写错误未核对 / 合并丢标题 / 替用户补话与改动机 |

### 修改

- **元原则 4 条 → 6 行**：新增「专有名词先核对」「差异不大就合并」，与原有四条同级
- **§1 结构**：新增 §1.1 转写核对，原 §1.1/1.2/1.3 顺延为 1.2/1.3/1.4
- **FM-5 扩写**：从「丢了已认可的划分」扩展为「**过度拆分**（本任务最主要的偏差）」，收入三条证据
- **交付格式**：新增「每个话题都必须有真标题」「未核实项另起 ⚠️ 待确认表」
- **自检 10 项 → 14 项**：新增专有名词核对、没替他补话、动机照原话、每个话题都有标题
- **提示词**：阶段 1 改为「转写核对 + 话题划分」；阶段 3 加合并补标题与不补话；阶段 4 自检 9 项 → 14 项；漂移表加 5 条

### 证据摘要（本轮）

| 缺陷 | 真实证据 |
|---|---|
| 转写错误未核对 | 「**ZEV** 第一系统模型」实为 **Jev**；「**DeepMind**」实为 **DeepSeek**（两名都是真公司，**不触发警觉**）；「大脑切片」实为**果蝇大脑切片** |
| 过度拆分 | 初划分 **12 个话题**；用户三轮要求合并 **3 次**、要求拆分 **0 次**，最终 **9 个**。其中一次拆分的理由原文是「原稿自己已经明确说『两个方面』『另外一方面』」——**把口语连接词当成了拆分依据** |
| 合并丢标题 | 输出写成 `**T5 + T6｜合并描述**`；用户回「**T5 + T6，怎么没有标题？**」 |
| 替用户补话 | 描述里被加了「我并不是现在遇到了一个'该选什么专业'的问题。更多就是单纯好奇，」；用户回「**没必要这么说明**」 |

## [1.0.0] — 首版

**规则来源**：一次知乎提问整理会话。用户给出口述稿（约 37 行、多话题混排、无小标题），要求整理成可发布提问。前后 **6 轮反馈、3 个版本**，用户连续退回 5 次。

### 案例 → 规则 映射

| 轮 | 用户反馈（原话节录） | 产出的规则 | 落在哪 |
|---|---|---|---|
| 1 | 「简要的提问（要符合内容，精准有力），还有问题的描述」 | 一个提问 = 一个核心矛盾 | `SKILL.md` §0 |
| 1 | （改稿者原则）「没有把自己的观点写成预设答案」 | 不写成预设答案 | `SKILL.md` §0、FM-7 |
| 2 | 「问题描述内容，要尽量贴合保留个人的语言风格」 | 保留六样（第一人称/场景/短句/口语连接词/具体名词/情绪） | `description-style.md` §1 |
| 2 | （改稿者自诊）「主要只做三件事——去重复、理顺逻辑、让别人能快速看懂」 | 只做三件事 | `description-style.md` §2 |
| 3 | 「第 4 个…**有点奇怪**」 | 标题太泛 = 像行业报告题目 | `title-craft.md` §1.1、FM-2 |
| 3 | 「**应该提到《凡人》这个作品吧**」 | 具体对象前置，抽象留给描述 | `title-craft.md` §3、FM-3 |
| 3 | （改稿者自诊）「抽象层级提得太早」 | 「标题给具体，描述做升华」的顺序 | `title-craft.md` §3 |
| 4 | 「你是不是忘了…**拆分多个问题**」 | 一个提问只抓一个矛盾点 | `topic-splitting.md` §2.D、FM-4 |
| 5 | 「**原来分出 7 点的文档挺好的**，内容再润色就行」 | 用户认可的划分不许再拆（元规则） | `topic-splitting.md` §2.D、FM-5 |
| 6 | 「**不够接地气，感觉太文绉绉的**」 | 「整理感」的三个诊断方法 | `description-style.md` §6、FM-1 |
| 6 | （改稿者自诊）「整理感太重，像专栏文章」 | 段落长度均匀是整理感的来源之一 | `description-style.md` §6 |

### 本仓库原创

| 新增 | 位置 | 说明 |
|---|---|---|
| **稿子 → 话题单元 → 核心矛盾 的六步方法** | `references/topic-splitting.md` | 原会话中**话题划分一次就对了**（7 个话题从未被质疑），所以**切分方法从未被显式写出来**。本仓库把它补成可执行过程：标记五类 → 按场景/矛盾对象切分 → 填充矛盾句式 → 双向粒度检测 → 优先级 → 产出 |
| **双向粒度检测** | 同上 §2.D | 原会话两个方向都栽过：轮 4 拆得不够（合成"大问题"），轮 5 拆过头（重新划分已认可的 7 点）。原会话只有教训，没有检测方法 |
| **「我看到 A，但实际是 B」的对齐句式** | 同上 §2.C | 把"一个核心矛盾"从口号变成可填空的判据 |
| **独立发布测试 / 场景测试 / 不重复测试** | 同上 §3 | 原会话靠人工退回，本仓库把判据前置 |
| **未采用清单** | 同上 §1 | 稿子里没进任何提问的内容必须写出去向与理由，防静默丢弃 |
| **标题三要素检查（具体对象 / 反差 / 口语）** | `title-craft.md` §1 | 从 7 个话题 × 3 个版本的真实对照里反推出来的 |
| **「整理感」的三个诊断法** | `description-style.md` §6 | 原会话只有"感觉文绉绉"这一句模糊判断 |

### 摘录政策（首版确立）

原产出含约 **4,100 字符个人生活内容**。仓库中：

| 内容 | 处置 |
|---|---|
| 7 个话题的**标题**（三版） | ✅ 收录（是标题规则的直接依据） |
| 反馈的**原话** | ✅ 收录（是失败模式的证据） |
| **一个话题**的完整描述 before/after（蓝牙耳机） | ✅ 收录（最清楚的一段对照，且题材最不私人） |
| 其余 6 个话题的**描述全文** | ❌ 不收录 |
| 原始口述稿 | ❌ 不收录（未提供，含个人内容） |

理由与边界写在 `references/worked-example.md` 开头。若日后需要全文存档，应放在**私有位置**，不要进这个公开仓库。
