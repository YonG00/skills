# Conversation Synthesis（对话合成）

一个用于**把长期对话整理成真正被思考过的文章**的 Agent Skill。

它把多轮、反复搜索、质疑、补充和修正的聊天记录，重建成一篇**有观点、有依据、有推理推进、有个人质感**的文章、研究笔记、分析稿或探索总结——而不是一份排版整齐的聊天纪要。

> 本仓库对应 `SKILL.md`（执行形态）与 `README.md`（可阅读的形态）。二者来自同一套知识体系：**Skill 是可执行的方法，Blog 是可阅读的方法。**

---

## 它解决什么问题

把一段长对话丢给通用模型"整理成文章"，最常见的失败不是"写不出来"，而是**写出来不像有人想过**：

| 失败模式 | 表现 |
|---|---|
| **按时间顺序复述** | 文章像会议纪要，读者不知道哪句是结论哪句是过程 |
| **没有判断变化也硬写** | 资料齐全、排版整齐，读完不知道"所以呢"——因为这段对话本来只是在收集资料 |
| **替用户说话** | 「我怀疑可能存在这种问题」被写成「事实证明就是这样」；助手的推演被塞进第一人称 |
| **用户修正被写回旧版** | 用户改过的措辞、强度、因果关系，重新生成全文后又变回去了 |
| **信息资产静默丢失** | 辛苦搜来的渠道、案例、工具、未完成线索，新稿里不见了，而且没人发现 |
| **资料倒灌** | 搜到了就都写进去，主线被淹没 |
| **写成"我后来发现…"的认知日记** | 初稿里「我」出现 **28 次**，几乎每段以作者的认知动作开头；**四个小标题全是第一人称叙事**（「四、我后来发现，accuracy 和 calibration 根本不是同一个问题」）。用户：「不要一直提"我干嘛"，是我去探索、去深究，但这事没必要一直说」 |
| **对话里的表格被拍平** | 对话里那张实验表（5 行方法 × Accuracy/ECE/Brier/置信度）在初稿里**整个消失**，只剩"表现更好"这种概括。用户：「之前的聊天内容中，不是有一些表格吗？怎么到文章内容就没有了？」 |
| **结尾硬凑"问题升级"** | 上游把"结尾必须回答五问"定为硬性要求，技术类文章里往往是在续尾巴。用户：「【没必要结尾升级吧】」 |
| **标题与小标题放到最后才给** | 旧流程把「标题候选」放在最后一个阶段，用户不得不在初稿写到一半时打断：「先确定大纲，下个阶段才是初稿」 |
| **章节按资料分类** | 结构是「数据 → 法律 → 国外案例 → 论文」，而不是问题推进 |
| **相关写成因果** | 研究说 A 与 B 相关，文章写成 A 导致 B |
| **AI 味** | 每段三点、每节都总结、每一页都金句、大量加粗、大量"本质上/赋能/范式" |
| **结尾没结束** | 停在「这个问题值得进一步思考」 |

本 skill 的每条规则都对应上面某一种可重复出现的失败模式——这是它的准入标准，不是装饰。

## 核心主张

### 1. 先还原问题链，才谈得上写文章

这是本版最重要的能力，也是最容易含糊过去的一步。上游规范给了一个**形状**：

```
最初的问题 → 第一次追问 → 新经历或反例 → 搜索与证据
→ 原判断被修正 → 新矛盾出现 → 问题继续推进 → 当前真正需要回答的问题
```

但**没有给从一堆混乱对话里推出这个链的过程**。本仓库补上了可执行的七阶段：**论元抽取 → 问题链重建 → 判断变化点识别 → 章节切分 → 资产归属与守恒核对 → 中心问题定稿 → 产出骨架表**。完整方法见 [`references/conversation-to-outline.md`](references/conversation-to-outline.md)。

三个关键判据：

- **一节 = 一次判断变化 + 支撑它的证据。** 判据是能否用一句话说清：「原来以为 X，因为 Y，现在认为 Z」。
- **全篇找不到一个判断变化点 → 不构成文章。** 这时该如实说"这段对话目前只是收集了资料"，而不是硬凑一篇探索文章。这是本仓库相对上游新增的**停止条件**。
- **论元与资产总数守恒。** 每一项都要有归属，删除必须给理由——而「删了以后文章更顺」**不是**理由。

### 2. 四条不可违背的元原则

```
问题链决定结构   →   不替用户说话   →   叙事顺畅 ≠ 事实成立   →   资产先回收再筛选
```

### 3. 保护用户真实性

不替用户下结论；不把助手观点塞进第一人称；用户后续修正**永远优先**；保留具体的时间、地点、动作，不把真实体验润色成空泛的"高级表达"。

个人经历是**问题入口**，不是社会统计——不能从「我经历过」直接跳到「社会上的人都这样」。

### 4. 事实可验证，观点可追踪，文章仍然能读

可核验内容（数字、法律、政策、研究、国外制度、机构定义）第一次出现时就给来源；来源有明确优先级链（法律原文 > 原始论文 > 权威组织 > 研究机构 > 可靠媒体 > 行业媒体 > 社区）。

但**观点不需要假装成文献**——用户经历、价值判断、明确标注的推演不需要强行挂链接。目标是三件事同时成立，而不是把文章变成参考文献列表。

### 5. 写作过程就是继续思考

每个重要判断都要被追问三遍（依据是什么 / 所以呢 / 真正想说什么）；主动找反例和限制；二元问题主动找中间态；识别系统激励；检查制度里纸面权利与实际资源的**不对称**；检查方案会不会制造新问题；建议要落到机制（谁负责、数据从哪来、多久一次、异常怎么办）。

### 6. 强调有节制，AI 感来自"过于整齐"

长文默认连续 prose；列表只在结构上真有价值时用；控制金句密度；反讽必须建立在事实矛盾上，而不是猜测别人动机。

> **AI 感往往不是因为某个词，而是因为所有段落都被加工得过于整齐。**

### 7. 修订是全文级的，Skill 更新是另一回事

用户指出一处问题 → 先判断是局部问题还是**全文级**错误 → 抽象 → 全文扫描 → 批量修正。

但**当前文章的反馈不自动等于 Skill 更新**：修完稿再单独判断哪些值得进入长期规则。而且只有通过通用性测试的才进——用户说"这里一个词一行看起来很碎"，**不能**写成"AI、机器人、芯片这类词不能一行一个"。

## 目录结构

```
conversation-synthesis/
├── SKILL.md                          # 可执行规范（主文件）
├── README.md                         # 本文件：为什么这样设计
├── CHANGELOG.md                      # 版本沿革与规则保留核对表
├── LICENSE
└── references/
    ├── conversation-to-outline.md    # ★ 本地原创：对话 → 文章骨架的七阶段方法
    ├── evidence.md                   # 第 23–28 条：证据覆盖、来源优先级、因果强度
    ├── argumentation.md              # 第 29–35 条：推进思考的分析清单
    ├── structure-and-style.md        # 第 36–50 条：结构、风格、排版、结尾
    ├── quality-audit.md              # 第 54–59 条 + 默认工作流
    ├── skill-maintenance.md          # 第 1–12 条 + 第十三～十七、十九部分
    ├── base-version.md               # 基础版存档（核对规则无丢失）
    └── reference-registry.md         # 外部知识入口索引
```

**规则资产 / 知识资产分离**：`SKILL.md` 与 `references/` 保存判断方法；外部来源只保存"路径"（URL），需要准确细节时沿着链接回到原文。

**文章级别的资料不进仓库**：具体文章用到的数据、案例、论文属于那篇文章的信息资产清单（见 `conversation-to-outline.md` Stage E），不是本 skill 的知识资产。

## 安装 / 使用

作为一个 Agent Skill 使用：把 `conversation-synthesis/` 整个目录放进你的 skills 目录即可（`SKILL.md` 带有 `name` / `description` frontmatter）。

作为提示词使用：直接读取并遵循 `SKILL.md`。

典型触发方式：

```
把这段聊天记录整理成一篇博客：<粘贴对话>
```

它应该先内部还原问题链与判断变化，再产出文章骨架（含「这一节不写什么」），然后成稿，最后跑六项审计。

## 更新本 skill

按 [`references/skill-maintenance.md`](references/skill-maintenance.md) 的工作流：

```
收集反馈 → 区分局部/任务/通用 → 跨主题通用性测试 → 建立旧规则清单
→ 优先整合 → 检查旧规则是否丢失 → 冲突交给用户决定
→ 逐项核对上一版：保留 / 合并 / 改写 / 建议删除 → 更新 CHANGELOG
```

三条硬约束：

1. **每条规则必须对应一个失败模式**——不为"看起来更完整"添加规则。
2. **旧规则默认保留**——重写不等于重新发明。即使要删，也应先标「建议删除：原因……」交给用户决定。
3. **新旧规则冲突不擅自决定**——方向相反、无法同时满足、合并会改变含义、要把"建议"升级为"必须"、会明显改变整体风格时，列出冲突交给用户。

## 还有哪些没有解决

- **问题链还原的质量仍依赖模型对整段对话的阅读能力。** 方法给了阶段、字段与守恒核对，但没有自动化校验：守恒核对与九项自检目前是**模型自检**，不是可执行测试。
- **「判断变化点」的识别没有客观阈值。** 目前只规定了"0 个不应成文"这条下限，多少个变化点才够撑起一篇文章仍靠判断。
- **超长对话（跨数十轮、上百条资产）的守恒核对**在实践上会很冗长；尚未定义分层抽样或摘要式核对的规则。
- **聊天模式提示词在仓库层，不在本目录。** 见 [`prompts/conversation-synthesis.md`](../prompts/conversation-synthesis.md)。本 skill 目录自身仍只有 `SKILL.md` 形态（需要文件系统）。
