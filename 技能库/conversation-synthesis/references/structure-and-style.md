## 第七部分：文章结构（第 36–39 条）

### 36. 先内部生成多个标题

正式写稿前，内部产生至少 5 个候选标题。

| 维度 | 内容 |
| --- | --- |
| 应同时具备 | 讨论对象；核心矛盾；信息增量 |
| 不要只追求 | 情绪；文艺；猎奇；学术感 |
| 数量要求 | 正式写稿前，内部产生至少 5 个候选标题 |
| 硬性约束 | 标题必须与正文真正匹配 |
| 防止的失败模式 | 原文未给出 |

### 37. 小标题必须独立成立

只读目录时，应该大致能知道文章在讲什么。标题应该承担导航功能。

| 类型 | 例子 |
| --- | --- |
| 差（避免） | 真正的问题；另一种可能；这里还有一个问题 |
| 好（优先） | 为什么 X 会产生 Y？；某种制度解决了什么，又留下什么？ |

| 项目 | 内容 |
| --- | --- |
| 检验方式 | 只读目录时，应该大致能知道文章在讲什么 |
| 作用 | 标题应该承担导航功能 |
| 防止的失败模式 | 原文未给出 |

### 38. 章节跟着问题变化，而不是资料分类

| 类型 | 结构 |
| --- | --- |
| 差（较差的结构） | 数据 → 法律 → 国外案例 → 论文 |
| 好（更好的结构） | 为什么原来的解释不够？→ 哪些证据改变了理解？→ 如果旧方案有问题，还有哪些中间方案？ |

较差的结构「因为这是资料分类」；更好的结构「每一节应该推进问题」。

| 项目 | 内容 |
| --- | --- |
| 判断标准 | 章节跟着问题变化，而不是资料分类 |
| 硬性约束 | 每一节应该推进问题 |

### 39. 新概念从问题中长出来

## 第八部分：写作风格与排版（第 40–47 条）

### 40. 长文默认使用连续 prose

文章应该像文章。如果多个短语能自然写成一句话，就不要拆成大量单独行。

连续出现三行以上极短内容时，检查：**真的需要列表吗？** 如果不需要，合并。

| 项目 | 内容 |
| --- | --- |
| 默认形态 | 长文默认使用连续 prose |
| 触发自查 | 连续出现三行以上极短内容时 |
| 处置 | 如果不需要列表，合并 |

### 46. 避免常见 AI 味

警惕高频使用：

| AI 味高频词 |
| --- |
| 本质上 |
| 真正 |
| 核心 |
| 值得关注 |
| 重新定义 |
| 范式 |
| 赋能 |
| 从某种意义上 |

| 项目 | 内容 |
| --- | --- |
| 结构化成瘾 | 每段三点；每节都总结；每一页都金句；过多加粗；过多反问 |
| 真正的成因（原文） | AI 感往往不是因为某个词，而是因为：所有段落都被加工得过于整齐 |

## 第九部分：结尾（第 48–50 条）

> **⚠️ 本部分已被 2.0.0 部分否决。** 上游第 48 条把"问题升级"定为**硬性要求**，实际使用中被用户明确反馈为多余：
>
> > 用户原话：「【**没必要结尾升级吧**】」
>
> 因此本文件保留第 48 条的**原文**（存档），但在下方给出**现行做法**。执行以现行做法为准。

### 48. 结尾必须完成“问题升级”（原文，存档）

结尾不是重复前文。至少应该回答：

- 开始时在问什么？
- 哪个理解后来发生了变化？
- 现在最可信的判断是什么？
- 还有什么不知道？
- 下一步真正应该问什么？

| 项目 | 内容 |
| --- | --- |
| 明确排除 | 结尾不是重复前文 |
| 最低要求 | 至少回答上述五个问题 |
| 防止的失败模式 | 结尾变成重复前文（没有完成“问题升级”） |

### 48-bis. 现行做法：收住，而不是强行升级（2.0.0）

**不强制回答五问。** 技术类文章尤其如此——方法、数据和边界都已经讲清楚，再追加一段"下一步该往哪走"往往是硬凑的。

**结尾的最低要求（三条，都必须满足）**：

1. **不重复** —— 不是把前文摘要一遍
2. **收得住** —— 最后一段要真的结束，不能停在「这个问题值得进一步思考」这类假结尾
3. **给出一个东西** —— 判断 / 更准确的认识 / 明确还缺什么，三者之一

**可选（不强制）**：如果文章**确实**推进出了一个新问题，可以点出来；**没有就不要造**。

判断标准：这个问题是在正文里真长出来的，还是为了收尾临时想出来的？

| 项目 | 内容 |
| --- | --- |
| 明确排除 | 机械回答五问；硬凑"下一步该验证什么" |
| 最低要求 | 不重复 / 收得住 / 给出一个东西 |
| 防止的失败模式 | 结尾硬凑升级，像在给文章续一个尾巴 |

### 49. 从具体场景开始的文章，可以考虑回环

- 如果开头使用一个具体经历，可以在结尾重新回来。
- 但不能原样重复。
- 应该用整篇文章得到的新理解重新解释这个场景。
- 回环只是一种结构工具。
- 不是所有文章都必须使用。

| 项目 | 内容 |
| --- | --- |
| 适用条件 | 从具体场景开始的文章，可以考虑回环 |
| 硬性约束 | 不能原样重复；应该用整篇文章得到的新理解重新解释这个场景 |
| 定位 | 回环只是一种结构工具，不是所有文章都必须使用 |
| 防止的失败模式 | 结尾原样重复开头的场景 |

### 50. 最后一段要真的“结束”

**避免：** 这个问题值得进一步思考。

如果前文已经进行了深入讨论，这种结尾相当于没结尾。

最后应该给读者一个：

- 判断；
- 新问题；
- 方法；
- 选择；
- 或更准确的认识。

| 类型 | 内容 |
| --- | --- |
| 差（避免） | 这个问题值得进一步思考。 |
| 好（应该给读者一个） | 判断；新问题；方法；选择；或更准确的认识 |

| 项目 | 内容 |
| --- | --- |
| 判断标准 | 最后一段要真的“结束” |
| 防止的失败模式 | 前文已深入讨论，结尾却只说“这个问题值得进一步思考”，相当于没结尾 |

## 补充：恢复自基础版第 12 条的两项风格要求

> **背景**：基础版第 12 条「语言风格」列了四项——**接地气 / 犀利 / 锐利 / 有洞见**。v3 只保留了「接地气」的独立条目（第 43 条），「犀利」被并入第 45 条「犀利不等于武断」，**「锐利」与「有洞见」没有独立对应条目**，且基础版的差/好对照例未保留。本仓库按「旧规则默认保留」原则恢复，理由见 `CHANGELOG.md`。

### 「锐利」= 找到问题里真正起作用的变量

不要停在表面现象。用户问一个问题时，继续追一层：

| 用户问 | 表面回答 | 锐利的追问 |
|---|---|---|
| 为什么这个方向竞争小？ | 因为没人做 | **是因为机会没人发现，还是因为根本没人买？** |

### 「有洞见」不是写一句漂亮金句

洞见 = **把原本分开的信息连起来**，找到更深一层的因果、矛盾或约束。

好的洞见通常能让**问题本身发生变化**：原来问"这个工具厉不厉害"，最后发现真正决定结果的是另一件事。

### 基础版保留的差/好对照例

| | 例子 |
|---|---|
| 差（大词） | `构建消费者洞察闭环。` |
| 好（具体） | `把评论、客服和退货原因重新拿回来，判断下一步该卖什么、改什么。` |

| | 例子 |
|---|---|
| 差（表面因果） | `Agent 很便宜，所以生意成本很低。` |
| 好（指出是两笔账） | `这是两笔账。Agent 便宜，不代表获客、物流和退货也便宜。` |

**人工确认项**：这两项是从基础版恢复的，不是 v3 的原意。若认为 v3 是有意合并（「锐利」≈ 第 30 条找反例、「有洞见」≈ 第 31 条找中间态），可以删除——但需按第十四部分标记「建议删除：原因……」交给用户决定，不要静默移除。

## 补充：叙事人称与作者提示语（2.0.0 新增）

> **来源**：一次真实的技术类文章调试。初稿里「我」出现 **28 次**，几乎每段都以作者的认知动作开头，连小标题都是第一人称叙事。用户回：「**不要一直提"我干嘛"，风格得变下，是我去探索，去深究，但这事没必要一直说。**」

### 探索感靠问题递进，不要靠"我发现"

| ✗ 日记式（初稿实际写法） | ✓ 结果式（定稿） |
|---|---|
| 我**最开始注意到** Jev，是因为它和我过去对大模型的理解有点冲突。 | 第一次看到 Jev 时，最反直觉的是它似乎走了一条和 reasoning model 相反的路。 |
| **后来我才意识到**，这个问题里其实混在了一起两件不同的事。 | 这里其实混着两件事。 |
| **刚看到这个名字时，我很容易产生一种感觉**：… | 这个名字容易让人以为背后有一个清楚的新 RL 算法。 |
| **后来我又去看**所谓的 Jev/RLCD 开源复现。 | 开源复现提供了另一组证据。 |
| **我最开始又把** calibration 和"按概率采样"混在了一起。 | calibration 和"按概率采样"是两件事，容易混。 |

### 小标题尤其不许用第一人称叙事

小标题承担**导航功能**，不是记录思路的地方。实际退回过的小标题：

```
✗ 四、我后来发现，accuracy 和 calibration 根本不是同一个问题
✗ 五、我最开始又把 calibration 和"按概率采样"混在了一起
✗ 六、到这里，我对"模型概率"的理解发生了一个比较重要的变化
✗ 七、这样再回头看 Jev，问题就已经和一开始不太一样了
```

**改法**：把"我如何转变"改成"问题如何变化"。

```
✓ 为什么模型可以不写一长串过程，直接给判断？
✓ 模型自己的概率分布，和现实发生频率是两回事
✓ Choice 后面的概率，为什么比答案更难处理？
```

### 语言基调（一句话记住）

> **像一个人认真把一个新技术一路查清楚，允许保留疑问和修正，但不把"探索者本人"放在每一段中央。**

### 要删的「作者提示语」

这类句子不提供信息，只是作者在给读者指路：

| ✗ | 为什么删 |
|---|---|
| 最初的问题很直接：… | 读者从正文能看出问题是什么 |
| 这首先解释了一个容易混淆的地方：… | 没有新增信息 |
| 更值得追下去的是另一个问题。 | 直接问那个问题 |
| 这里至少有三点值得注意。 | 直接说那三点 |
| 这样看，X 并不是最难解释的部分。 | **"最难"这类高低排序是 AI 套路**，且会制造"真正的问题在后面"的预期 |
| 我们先把 X 放一放，来看 Y。 | 直接讲 Y |

**判断方法**：删掉这句，读者会不会看不懂？**不会 → 删。**

### 自检

- [ ] 「我」出现了多少次？含第一人称叙事的段落占全文多少？**技术类文章不应超过 1/4**
- [ ] 小标题里有没有「我后来发现」「我最开始」这类叙事？
- [ ] 有没有「最初的问题很直接」「更值得追下去的是」这类作者提示语？
- [ ] 连续单句成段、短反问、刻意对仗是否过多？（初稿实际被删掉了「模型内部没有矛盾，错的是现实估计」这类刻意对仗）
