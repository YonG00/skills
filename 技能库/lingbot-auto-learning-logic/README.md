# LingBot-VLA-v2 自动学习逻辑地图（Auto Learning Logic Map）

一份**改代码前必须读**的 Auto Learning（AL）系统地图：把"任务怎么被选、怎么被评测、怎么被判 PASS/DEFER/EXHAUSTED、池子怎么演进、存档怎么落盘"整条链路写成一篇可检索的参考。

> 本仓库对应 `SKILL.md`（执行形态）与 `README.md`（可阅读的形态）。二者来自同一套知识体系。

规则来源：**不是上游文档，而是这台机器上真实跑出来的事故与实测数字**——每一次崩溃、每一个"指标对不上"、每一条"改了没生效"，都收敛成这里的一条。

---

## 它解决什么问题

AL 是一个**多层状态机 + 多进程评测 + 多份缓存 + 多套存档**的系统。改一处很容易静默失效另一处：

| 典型症状 | 真实原因 | 本文对应节 |
|---|---|---|
| 训练跑着，面板显示"无进程!" | 面板从 `TRAIN_OUT` basename 取 run 名，**假定带 `train_` 前缀**（显式 `--train-out` 后不带） | §9 |
| 判定失效，**0 个 PASS** | 轨迹分片切在"多卡协议**之外**"⇒ 框架"只有 rank0 算数 + 广播"把各卡切片作废 | §2 附 |
| 单卡扫描数值与历史差 0.5–4.7 倍 | 并行窗口逻辑**没加 `world > 1` 门槛**，污染了单卡口径 | §11 |
| 面板"在训 `A`"但实际在训 `B` | 判据用了 `unit_loss`（**unit 结束时**才写）⇒ 它代表"刚训完的" | §9 附 |
| 训练在存档点**直接崩**（`assert metadata is not None`） | `final_only` 下周期不写 DCP，而旧 HF 路径**必须读 DCP** | §13 附 |
| 停机后**一个存档都没有** | 收尾 DCP 的容量闸门用**保守常量**（≈72 G）判空间，输出目录在小盘上 | §13 附 |
| "早就过线了怎么还在学？" | 面板/事件流的 `step` 是 **AL 内部步**，不是全局步 | §9 附 |

## 核心内容

### 数据与判定（§1–§3）

- 任务 / 回合 / 帧的三层模型；`sample_id` 全程不变的前提
- 四个评测 split（`scout` / `confirm` / `active_val` / `train_monitor`）的**条数、时机、是否真推理**
- 三把尺子：`mse` / `nmse`（legacy 显示量）/ **`gmean_mse`（当前判定口径）**，以及阈值表怎么标定（`multiplier=60`）

### 状态机与成本（§4–§6）

- bootstrap 免费 PASS、`select` 只挑 CANDIDATE、rescan 的"免费 PASS 检测"
- **attempt / reopen 的真实语义**（§4 附）：`max_attempts` 管"被选中几次"、**跨 run 继承**、
  `max_reopens_per_task` 在 `max_attempts=2` 下**永远不可达**、有效复习只有 1 次
- review 开关的两面：关掉能"PASS 只增不减"，但**遗忘不可见**、且**只省 ≈1% 算力**、
  **不加速覆盖新任务**；而复习**确实有效**（实测一个崩到 6.75 倍的任务 50 步救回）

### 观测与成本模型（§9）

- **三套步号**（全局步 / AL 内部步 / unit 数）的换算与误判案例
- **任务周期的成本模型**：训练 80% + hardness 扫描 15% + 评测 3% ⇒ 一个任务 ≈21.7 分钟；
  覆盖速度的决定性杠杆是 `eval_interval_steps`（50→10 ⇒ 4.8×）
- 配置自洽的硬校验（整数倍约束、`hf_pass_interval` 与 `save_hf_weights` 互斥、
  `--steps` 是绝对步号 ⇒ 写小了"一步都不跑"）

### 存档（§13 + §13 附）

- 池子独立存档 `pool_state.json` 的三条恢复路径与 6 个 `AL_POOL_STATE_*` 开关
- **存档策略四象限**：哪格正常、哪格必崩、`final_only × save_hf_weights=true` 为什么崩
- HF 的两条写路径（DCP 转档 vs **内存直出**）与"与 unit 边界解耦"
- 精度开关与体积：`enable_mixed_precision` / `enable_fp32` / `hf_export_dtype` 各自管什么

### 台账（§10–§12）

- 已确认的逻辑冲突（门控与基线互斥、重复评测、参数语义错位）
- 硬约束与踩坑台账（训练期禁跑 GPU 测试、停训必须按进程组、共享文件必须带指纹……）
- **§12 待验证改动**：哪些改动默认生效、哪些只 CPU 验过、哪些默认关 —— 上机报错先来这里对号

## 怎么用

| 场景 | 读哪里 |
|---|---|
| 要改 AL 代码 | 先 §10（已知冲突）→ §11（踩坑）→ 要改的那一节 |
| 上机报错、怀疑是某条改动 | **§12**（含"读逻辑时要注意什么"与"未验证的风险"） |
| 面板数字看着不对 | §9 + §9 附（数据源与新鲜度、三套步号） |
| 判定异常（0 PASS / 指标 None） | §2 附（分片正确架构、fail-closed 条件） |
| 存档相关 | §13 / §13 附（四象限、容量闸门、精度与体积） |
| 要提速 / 提高覆盖率 | §9 附 2（成本模型与杠杆表） |

配套的**权威账本**在项目仓库内：`docs/auto_learning/AL_PENDING_CHANGES.md`
（每条改动的 §1 待验证 / §2 已验证 / §3 遗留，含 commit SHA 与「改动本意」四问）。

## 与另一个技能的分工

| | 本技能 | `lingbot-code-changes` |
|---|---|---|
| 管什么 | **系统是什么样**（结构、口径、成本、已知冲突） | **怎么改才不出事**（讨论 → 清单 → 逐条执行 → 提交） |
| 输出 | 逻辑地图 + 踩坑台账 | 流程 + 验证矩阵 + 台账登记规矩 |
| 何时读 | 动手前、排查时 | 每次真的要改代码时 |
