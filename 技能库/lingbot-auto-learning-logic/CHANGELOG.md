# CHANGELOG

本文件记录本 skill 的规则来源与演进。

## 来源性质

| | 本 skill | 仓库另两个 skill（`technical-course-private-tutor` / `conversation-synthesis`） |
|---|---|---|
| 上游 | **无公开文档** | 博客园等公开文章（有版本链） |

## [1.3.0] — 存档策略组合、attempt 语义、覆盖率成本模型

**规则来源**：2026-10-12 ~ 10-13 的一次完整训练事故链（`al_v65 → v76`）。

### 新增 §13 附：存档策略组合表（**最重要**）

| 事故 | 规则 |
|---|---|
| `dcp_save_mode=final_only` + `save_hf_weights=true` ⇒ **训练在 step 2600 崩**（`CheckpointException ranks:[0]` + `state_dict_loader.py: assert metadata is not None`），已训 44 分钟 + 池子全丢。根因：`final_only` 周期不写 DCP，而旧 HF 路径 `ckpt_to_state_dict → dcp_to_torch_state_dict` **必须读 `<ckpt>/model` 的 DCP** | 加"**四象限表**"：哪格正常、哪格必崩；并把修法（改用 `export_model_hf_direct` **内存直出**）写进规则 |
| 修复后"验证通过"，正式跑却仍崩（另一次事故） | 加"**验证必须覆盖真正会出问题的那条分支**"：`--steps 10`（< `step_offset`）只会走**收尾**分支；周期分支必须 `--steps > offset + N` |
| 停机前凭记忆估 DCP ≈24 G，实际闸门预判 ≈72 G ⇒ 56 G 可用空间下**收尾存档被跳过**（停了机、什么都没存下） | 加"**停机/存档前先跑容量预判，输出目录放大盘**"；记录闸门用**保守常量** |
| `save_steps=3` 名义 3 步、实际被推到 unit 边界（50 步） | 加"**HF 直出与 DCP 延迟解耦**"：HF 不做 resume ⇒ 不受 `at_boundary` 约束 ⇒ 独立触发在 `_save_due` 判定之前 |
| `HF_PASS_INTERVAL`（脚本默认 **2**）与 `save_hf_weights=true` **互斥** ⇒ `ValueError` 启动即崩（踩了两次） | 加进 §9 附 3"配置自洽的硬校验" |

### 新增 §4 附：attempt / reopen / 复查 的真实语义

| 实测发现 | 规则 |
|---|---|
| `attempt_count` **跨 run 继承**（池子带入）⇒ al_v76 的 20 个被选中任务里 **12 个选中时 `attempt` 已是 2** ⇒ 本 run 一选中就用满预算，**一遗忘就永久 EXHAUSTED** | 写清四个参数的**真实管辖范围**，并给出 `select` 事件里的 `attempt` 字段作为判据 |
| `max_reopens_per_task: 3` 在 `max_attempts_per_task: 2` 下**永远不可达**（有效复习 = 1 次） | 显式标出"配置写了但无效"的参数 |
| 7 个任务被 reopen 成 CANDIDATE，**却没有任何任务被选中 ≥2 次**（`_select()` 优先"从未尝试过的新任务"） | 加"'有额度'≠'排得上队'"，指出"队列长度"与"复习机会"的耦合 |
| `review_after_task_transitions: 0` 能完全关闭复查（`apply_reopen` 是唯一把 PASS 改回 CANDIDATE 的入口，只被 review 调用） | 给出关闭开关的**收益（PASS 只增不减）/ 代价（遗忘不可见、省 ≈1% 算力、不加速覆盖）** |
| `stack_bowls_three` 退化到 **nmse 1.274 / 倍率 6.75×** 被判遗忘 ⇒ **复习 50 步救回**（val mse 0.1446 → 0.0081，倍率 0.68×） | 作为"'复习'确实有效"的**反例证据**，防止下次轻率关掉 review |

### 新增 §9 附：三套步号 + 覆盖率成本模型

| 实测发现 | 规则 |
|---|---|
| 面板"历史"行用的是 **AL 内部步**（事件流 `step`），不是全局步（`tb_step` / `global_step_N`）⇒ 用户困惑"G 早就过线怎么还在学" | 加"三套步号别混"表 + 报数优先用 `tb_step` |
| 任务周期实测 **21.7 分钟** = 训练 2 unit（17.3 min，80%）+ hardness 扫描（191 s，15%）+ 评测（40 s，3%）；**23 个新任务 ⇒ ≈8.3 小时** | 加成本模型 + 杠杆表（`eval_interval_steps 50→10` ⇒ 4.8×；`hardness` 帧上限 ⇒ 省 15%；`review` 关闭 ⇒ **不解决覆盖率**） |

### §9 修正：面板「在训任务」判据是错的

- 原技能写"在练任务 = 事件流 `task/<t>/unit_loss`（step 最大者）"；
- **实测它会把"刚训完的任务"当成"正在训的任务"**（al_v76：显示 `stack_bowls_three`，实际 `place_object_scale`）；
- 改为：**事件流最后一条 `select` 事件** → `curriculum/current_task_name` → 兜底才用 `unit_loss`。

### §12 新增 4 行（HF 直出 / 解耦 / 面板两项修复）

含"读逻辑时要注意什么 / 未验证的风险 / 状态"，全部标注实测数字与证据命令。

## [1.2.0] — 分片正确架构与两条"静默改口径"教训（2026-10-12）

| 事故 | 规则 |
|---|---|
| 轨迹分片切在"多卡协议**之外**" ⇒ 框架"只有 rank0 算数 + 广播"把各卡切片作废 ⇒ `gmean_mse` fail-closed 返回 None ⇒ **0 个 PASS** | 写进 §2 附"**分片正确架构**"：切片与归并都必须**在协议之内** |
| 共享白名单文件名 `<tag>.json` 在多卡下互相覆盖 ⇒ 后到 rank 读到**别人的切片**（实测 `rank2 run_ids=[1408]` 却返回 `per_traj_ids=[1403]`） | §11 分片专项 1：**共享文件名必须带内容指纹** |
| 并行窗口逻辑没加 `world > 1` 门槛 ⇒ 单卡的"每 50 帧一个窗口"被改成"每条轨迹摊 2 个窗口" ⇒ 同一轨迹 MSE 差 **0.5–4.7 倍**、43/50 任务与历史不一致，而程序不报错 | §11 分片专项 2：**设备数相关分支必须显式门槛** + 单卡回归验证 |
| `set_shard_merge_strategy(...)` 用 `try/finally` 立刻清 ⇒ 与各卡返回时序竞态 | §11 分片专项 3：**只注入、不收回**（策略幂等） |
