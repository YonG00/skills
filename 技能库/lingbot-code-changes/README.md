# 分阶段受控代码改动（Controlled Code Changes）

一套**改生产代码/长跑训练代码**的受控流程：**讨论 → 清单 → 逐条执行 → 提交**。每一步都要用户确认后才进入下一步。

> 本仓库对应 `SKILL.md`（执行形态）与 `README.md`（可阅读的形态）。二者来自同一套知识体系。

规则来源：**不是上游文档，而是本机 LingBot-VLA-v2 多轮真机改动中，被用户退回/被事故打出来的规矩**。

---

## 它解决什么问题

在"后台正跑着 7 卡长训练、不能随便起测试"的环境里改代码，有三个反复出现的失败模式：

| 失败模式 | 后果 | 本流程的对策 |
|---|---|---|
| **一口气改完** | 出问题时无法归因是哪一处引起的 | 拆成最小改动单元，**一次只改一条**、每条改完立刻最小验证、每条都等用户同意 |
| **改了没上机验证** | 报错时不知道"是不是我改的" | **改动台账**（`docs/auto_learning/AL_PENDING_CHANGES.md`）+ 状态四档；报错先读台账 |
| **验证只走了顺路的那条分支** | 宣布"可用"，正式跑却崩（真实事故：丢了 44 分钟训练） | **组合类改动的「验证矩阵」**：凡"开关 × 开关"，四象限逐格给证据，没验的要写"未验证" |

---

## 四个阶段

| 阶段 | 产出 | 不许做什么 |
|---|---|---|
| **1 讨论** | 五块内容：需求复述 / 现状 / **逻辑冲突** / 方案候选 / 我的建议 | **不写任何代码**；思路没定不进阶段 2 |
| **2 清单** | 可单独执行、可单独回滚的最小改动单元（每条含"改前/改后"关键代码） | 不在阶段 2 里顺手加没被批准的条目 |
| **3 执行** | 每条固定四段：原逻辑 / 新逻辑 / 关键改动 / **实测验证数字** | 一次只改一条；超出清单范围要重新报批 |
| **4 提交** | 测试数字 → `commit -F` → 单独 push → 文档与经验三处落地 | 测试未全绿不提交；文档缺一处不算完成 |

## 两个核心遗留物（这是本技能最有价值的部分）

### 1. 改动台账

位置固定：项目仓库内 `docs/auto_learning/AL_PENDING_CHANGES.md`，三个分区：

| 分区 | 内容 |
|---|---|
| **§1 待验证** | 每条一行：编号 / 日期 / 改什么（文件+函数）/ 为什么 / 期望判据 / 依赖冲突 / commit / 状态 |
| **§2 已验证** | 上机跑通后移入，写清**验证方式 + 实测数字**（并把"症状 + 回滚"一起带过去） |
| **§3 已知遗留** | 写明"为什么暂不改"（改动面 / 历史可比性 / 影响外部工具） |

状态四档：`⏳ 待验证` / `🧪 部分验证（只有 CPU 证据）` / `✅ 已验证` / `↩️ 已回滚`。

**为什么它是核心**：改动会不断积累、很多**改了但没上机验**。出问题时，"这是哪个改动引起的"
比翻 git log 快得多——**先读台账 §1 与 §3**。

### 2. 「改动本意」四问

每条改动除"为什么改"以外，**必须**写四件可检验的事（写不出来 = 没写）：

| # | 写什么 | 合格判据 |
|---|---|---|
| 1 | **不变量** | 能用一条断言/命令验的性质（例："`disabled` 为空时 RNG 状态逐位不变"） |
| 2 | **出错症状** | 指向具体可观测物（日志字符串 / 事件字段 / 崩溃栈），并能与别的故障区分 |
| 3 | **快速回滚** | 可执行动作（开关名+取值 / `git checkout`），并**注明开关的读取时机** |
| 4 | **验证入口** | 一条命令或一段日志匹配式 |

## 组合类改动的「验证矩阵」

凡"开关 × 开关"的改动，交付前必须给出四象限矩阵，且**每一格都要有证据**：

| | 开关 B = off | 开关 B = on |
|---|---|---|
| **开关 A = 主流值** | 回归/历史逐字一致 | 必须有证据 |
| **开关 A = 另一值** | 必须有证据 | **必须有证据**（真实事故就栽在这格） |

每格写清：**走哪条分支**（函数名/日志字符串）+ **怎么验的** + **结果**；
同一格内还有多条分支（周期 / 轮末 / 收尾）时，要说明**覆盖了哪几条**。

## 常见坑（节选）

完整清单见 `SKILL.md` 的「常见坑」。代表性几条：

- **别把"用户同意的那一步"扩权**：只做被批准的那一条。
- **配置类改动要验证"真的生效"**：查进程环境或日志里的策略行，不能只看命令里写了。
- **锚点用谓词不用行号**。
- **回复排版：表格单元格里绝不放多行/代码块**（会被渲染崩坏）——用"表格 + 表格外代码块"两段式。
- **并行/分片类改动先问"这个分支该不该管单卡"**：必须显式 `if world > 1` 门槛，并做单卡回归。
- **共享文件名必须带内容指纹**（多进程各卡输入不同的场景）。
- **验证要覆盖真正会出问题的那条路径**，不能只验顺路的那条。
- **传参前先读校验代码**（互斥参数会让进程 0 秒退出）。
- **停机/存档前先跑容量预判**，不要用记忆里的体积数字。
- **步号有两套以上，报数必须带口径**。
- **别用 `echo/grep` 把模式串写进同一条命令**（自匹配假警报）。
