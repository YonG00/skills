# 分阶段受控代码改动（讨论 → 清单 → 逐条执行 → 提交）

## 何时用

- 用户要改代码（功能 / 修复 / 重构 / 配置 / 训练脚本），且**不希望一口气全改完**。
- 用户说过类似："先跟我讨论思路"、"列个改动列表我确认"、"一个一个改、我同意再下一个"、"测试没问题、我满意了再 push"。
- 涉及**生产训练 / 长跑任务 / 多人协作仓库**的改动 ⇒ 必须走这个流程。

## 铁律（优先级高于流程本身）

1. **未经用户点头，绝不写代码 / 改配置 / 起停进程 / 提交 / push**。默认动作 = **只读取证 + 讲清楚 + 给选项**。
2. **不扩权**：用户同意第 3 条改动，不等于同意第 4 条或"顺手重构"。一次只做被批准的那一条。
3. **报错时的默认动作是取证不是"先修修看"**：先只读讲清现象、根因、影响面，给选项等用户决定。
4. **不得对后台作业使用等待语义**（`wait=true` / `timeout_ms` 等）；长任务一律后台发起，完成后由通知接结果。
5. 用户可见的一切说明用**中文**；涉及数值必须给实测值，不写"大概/应该"。
6. **涉密处理**：清单与解释里可以写"改哪个文件、哪一类逻辑、做什么"，但**不贴**密钥、token、内网 IP、端口、主机名、账号、私有路径等敏感原值（用 `<主机>`、`<端口>`、`<密钥路径>` 指代）。

## 改动台账（2026-10-11 用户要求 · **本流程的核心遗留物**）

**背景**：改动会不断积累，很多功能**改了但没上机验证**（后台在跑训练、不能起 GPU 测试）。
于是需要一个"账本"回答：**改了什么 / 为什么改 / 期望什么 / 和谁冲突** ——
否则以后一报错，就得从零推理"这是哪个改动引起的"。

**台账位置（固定）**：`docs/auto_learning/AL_PENDING_CHANGES.md`（仓库内，随代码提交）。
三个分区：
- **§1 待验证**：每条一行，字段固定 —— 编号 / 日期 / 改什么（文件+函数）/ **为什么** / **期望行为（判据）** / 依赖或冲突 / commit / 状态；
- **§2 已验证**：上机跑通、用户确认可用后移到这里，**写清验证方式与实测数字**；
- **§3 已知遗留 / 暂不改**：写明"为什么暂不改"（改动面 / 历史可比性 / 影响外部工具）。

**状态取值**：`⏳ 待验证`（已改未上机）/ `🧪 部分验证`（只有 CPU 证据）/ `✅ 已验证` / `↩️ 已回滚`。

**落到流程里的动作（缺一不可）**：
1. **阶段 3**：每落地一条改动 ⇒ **立刻在 §1 追加一行**（禁止"等以后一起补"）；
2. **阶段 4**：提交后补 commit SHA；若该轮有上机验证 ⇒ 更新状态并写实测数字；
3. **每轮收尾**：检查 §1 里是否有"其实已经验证过"的条目 ⇒ 及时移入 §2（**用户明确说过：跑了能用后就不必再惦记**）；
4. **报错时**：先读台账 §1 与 §3，判断"是不是某个未验证改动引起的" ⇒ 再决定修法（这条比翻 git log 快得多）。

**目的**：新增会话/新 agent 打开台账就能接续工作，不必依赖对话历史。

### 「改动本意」四问（2026-10-12 用户要求：**记下修改的本意，方便后面出问题 debug**）

**背景**：台账原来只有"为什么改"（动机，面向文档）。真出问题时，要回答的却是**另一组问题** ——
"这是不是我改的？它现在算不算坏？怎么立刻退回去？"。所以每条改动**除动机之外**必须写四件事：

| # | 要写什么 | 判据（写不出来 = 没写） | 反例（**禁止**） |
|---|---|---|---|
| 1 | **不变量**：改完后**永远必须成立**的性质 | 可检验：能用一条断言 / 一条命令验 | ❌"为了省开销"（那是动机）<br>✅"`disabled` 为空时，取 item 前后 RNG 状态**逐位不变**" |
| 2 | **出错症状**：坏了**长什么样** | 指向**具体**可观测物（日志字符串 / 事件字段 / 指标 / 崩溃栈），并说明怎么与别的故障区分 | ❌"可能有问题"<br>✅"训练同 seed 两次结果不同"、或"日志里缺 `pool_filter 生效` 字样" |
| 3 | **快速回滚**：一步退回去 | 给**可执行动作**：开关名+取值 / `git checkout <file>` / 删某段早退；**开关要注明读取时机**（进程启动读一次 ⇒ 必须重启才生效） | ❌"回滚改动"<br>✅"`AL_EVAL_SHARD=0`（默认已关）"、"`AL_HARDNESS_FORCE_SNAPSHOT=1`（**需重启**）" |
| 4 | **验证入口**：怎么确认它**还在生效** | 一条命令 / 一段日志匹配式 | ❌"跑一下就知道"<br>✅"`pytest tests/test_al_deterministic_sampling.py`"、"日志出现 `[open_loop][shard] world=7 local=2 merged=4/4`" |

**落到流程里**：
- **阶段 3** 每落地一条 ⇒ 台账 §1 追加时**同时**写这四问（可压进"期望行为/依赖"列，但**四问缺一不可**；
  一行放不下就在该条下面加一行缩进说明）；
- 条目**移入 §2** 时 ⇒ **把"症状 + 回滚"一起带过去**（§2 原来只记验证证据 ⇒ 不够：排查时仍要知道"坏了什么样、怎么退"）；
- **开关集中登记**：所有 `AL_*` 开关在台账里有一张**总表**（开关名 / 默认值 / 何时读取 / 作用 / 回退语义），
  排查时不必翻代码找"到底有没有这个开关"。

## 阶段 1 · 需求 → 代码 → 讨论思路

目标：**先把"需求"与"现状"都读准，再谈方案**；不写任何代码。

1. 先**读代码**（`grep`/`read`）确认用户描述对应的真实实现位置与当前行为；
2. 输出五块内容（顺序固定）：
   - **我对需求的理解（复述）**（2026-10-11 用户要求）：用**自己的话**把用户要什么、
     不要什么、边界在哪列成清单（逐条 1/2/3…），**并显式写出"我可能理解错的地方"**，
     请用户先纠正。理由：需求理解错 ⇒ 后面三个阶段全是白做，这一步比读代码更该先确认。
   - **现状**：相关代码在哪、现在怎么跑、关键约束（含实测数据）；
   - **逻辑冲突**（2026-10-11 用户要求）：把"**代码现状与需求之间**"以及"**代码内部自相矛盾**"
     的地方逐条列出，每条必须给：冲突点 / 证据（代码位置 + 实测数字）/ 为什么会冲突 /
     影响是什么（谁静默失效、白花什么）/ 可选的消解方向。**不要只讲"能做"，要先讲"哪里不通"**。
     典型来源：门控与基线的互斥（A 任务测的值 B 任务用不上）、同一批数据被评两次、
     复核集是初筛集的超集（不独立）、参数语义与用途错位（名字说 A 实际当 B 用）。
   - **方案候选**：2–3 个思路，各写清 **代价 / 风险 / 影响面 / 是否可回滚**；
   - **我的建议**：明确推荐一个并说明理由，标出我不确定的点（需要用户裁决）。
3. 用户讲的需求与代码现状**不一致时，直接指出**（"你说的是 X，但代码里是 Y，证据是 …"），不要顺着讲。
4. 讨论到用户说"就按这个思路"为止；**思路没定，不进入阶段 2**。
5. **需求理解未获用户确认前，不得输出阶段 2 清单**（哪怕方案已经想清楚）。

## 阶段 2 · 拆成小改动清单（交用户审阅）

目标：把方案拆成**可单独执行、可单独回滚的最小改动单元**，形成列表让用户改。

清单里每条必须含（缺一不可）：

| 字段 | 内容 |
|---|---|
| **编号** | `1`、`2`…（后续执行与撤回都引用这个编号） |
| **改哪里** | 文件 + 锚点（函数名/行为准，**不写死行号**，行号会失效） |
| **怎么改** | 具体动作（新增/替换/删除哪段逻辑），关键处给**示意代码** |
| **为什么** | 动机 + 依据（实测数据 / 报错 / 需求原文） |
| **影响面** | 会动到哪些调用方、配置、缓存、产物；是否需要重启/重跑 |
| **风险与回滚** | 最坏情况 + 怎么撤（`git checkout <file>` / 还原某个开关） |
| **依赖** | 依赖哪条先做（有则写编号） |

附加要求：
- 清单**只讲逻辑层级**，可含示意代码片段，但**脱敏**（见铁律 6）；
- **必须给出"关键代码/函数示意"**（2026-10-11 用户要求）：每条改动都要贴出
  **改前 / 改后的关键行或函数骨架**（伪代码亦可，但要精确到变量名与分支），
  不能只写"修改某函数"。理由：只有文字描述时用户无法判断改动是否真的落在对的地方，
  也无法预判数值口径变化；贴出关键代码后用户可在阶段 2 就否掉错误方案。

### 🔴 清单的**排版规范**（2026-10-12 用户指出"输出格式有问题，好几次都这样"）

**根因（我犯的）**：把**多行代码块塞进 Markdown 表格的单元格** ⇒ 单元格不能含换行，
表格必然渲染崩坏（前几轮"清单渲染乱掉"就是这个原因，不是内容问题）。

**规矩（写清单时强制）**：
1. **表格单元格只放短内容**：一段话 / 一个词 / 一行内联代码（`` `like_this` ``）；
2. **代码一律放表格外面**，用"**改哪里 → 代码示意**"两段式：
   ```
   #### 编号 N —— 一句话
   | 字段 | 内容 |          ← 表格：只有 改哪里/为什么/影响面/风险与回滚/依赖（短句）
   （表格结束）

   **改前**
   ```python
   ...
   ```
   **改后**
   ```python
   ...
   ```
   ```
3. **单元格里禁止**：多行、代码块围栏（```）、裸换行、长表格嵌套；
   多行内容一律拆成"表格 + 表格外的正文/代码块"；
4. **自检**：发清单前扫一遍 —— 每个 `|` 行的**单元格内是否还有换行**？有 ⇒ 拆出去。

**同一坑的其它表现**（都要避免）：
- 把"改前/改后"塞进同一单元格 ⇒ 拆成两个代码块；
- 表格里写多行 `- 列表` ⇒ 移到表格下；
- 用 `<br>` 硬凑多行 ⇒ 不用（渲染不统一），改用"表格 + 正文"。
- **必须列出"连带改动"（影响面证据）**（2026-10-11 用户要求，实战踩坑）：
  改一处前先 `grep` 全仓引用点，把**会被同一语义牵连**的地方逐条列出（调用方、对照组/基线、
  标定工具、测试、持久化字段），并明确"不同步改会怎样静默失效"。
  实例：删除 AL 的 `active_val` 口径时，`orchestration/baselines.py` 的对照组用同一个
  `EvalSplit` + `is_pass()` 判定，不同步改会让**实验组/对照组对比静默失效且不报错**。
- 明确标出**本次不做**的项（避免用户以为包含）；
- 结尾问一句："哪几条要改 / 删 / 合并？确认后我按顺序逐条执行。"

## 阶段 3 · 逐条执行（每条都要同意）

对清单里的**每一条**，固定输出四段：

1. **原代码逻辑**：改之前它怎么工作（贴关键片段，脱敏）；
2. **新代码逻辑**：改之后怎么工作（贴关键片段）；
3. **关键改动**：这次真正变的是哪一两行/哪个分支，为什么这么写；
4. **验证结果**：语法/单测/实跑证据 —— 用**实测数字**（如 `21 passed`、`Step: 950`、`10.9 s/it`），不写"应该没问题"。

然后**停下来等用户**：
- 同意 ⇒ 做下一条；
- 不同意 ⇒ 按用户意见**修改**或**撤回**（撤回时给 `git checkout` 命令或反向补丁，并复跑验证）；
- 用户要求调整顺序 ⇒ 记录新顺序再继续。

执行纪律：
- 一次只改**一条**；改完**立刻**做该条的最小验证；
- 多条改动落同一文件时，**逐条提交 diff 范围**要能对上编号，避免混在一起；
- 任何一条实际改动超出清单范围 ⇒ **停下来重新报批**。
- **适当增加日志与注释**（2026-10-11 用户要求）：改动落地时**同时**补
  ① **运行期日志**（关键分支/取值/省下的量，例如"confirm 复用 scout N 条、新评 M 条"），
     让外部只看日志就能判断"这次到底做了什么、有没有生效"；
  ② **代码注释**（为什么这么改、不这么改会怎样、对外口径是否变化）。
  日志要求：**用 rank0 或 info_rank0 级、不刷屏、含可核对的数字**；
  禁止"只改逻辑不留痕"（否则事后无法从产物判断是否生效，只能翻代码）。

## 🔴 组合类改动的「验证矩阵」（2026-10-13 用户要求，因一次真实事故补入）

**背景**：本次改动是"两个开关的组合行为"（`dcp_save_mode` × `save_hf_weights`），
四个象限里**只有一个会崩**（`final_only × true`）。我只验证了其中一个象限的**一条顺路分支**
（收尾存档），就宣布"可用"⇒ 正式跑起来在**另一条分支**（周期存档）崩掉，丢了 44 分钟训练。

**规矩：凡是"开关 × 开关""模式 × 模式"的改动，交付前必须给出四象限矩阵，并逐格标注证据**：

| | 开关 B = off | 开关 B = on |
|---|---|---|
| **开关 A = 默认/主流值** | 必须有证据（回归/同历史逐字一致） | 必须有证据 |
| **开关 A = 另一值** | 必须有证据 | **必须有证据（本次就栽在这格）** |

- 每格写清：**走哪条分支**（函数名/日志字符串）+ **怎么验的**（命令或参数）+ **结果**；
- **"没验"要显式写"未验证"**，不许留空、不许用"应该没问题"填空；
- **同一格里还有多条分支时**（周期 / 轮末 / 收尾），要说明**验证覆盖了哪几条**——
  本次事故的本质就是"收尾分支验了、周期分支没验"；
- 主流值那一列优先用**回归证据**（跑既有脚本，证明与改动前逐字/逐值一致），
  非主流值那一列用**定点实验**（小 `max_steps`/小 `save_steps` 把目标分支打出来）。

**推论（写进清单里）**：阶段 2 的清单每条都要有"影响面"，若影响面里出现**组合**，
就把上面这张矩阵一并列出来当**验收条件**；阶段 3 每落一条 ⇒ 立刻填对应格。



**原则：凡是"读起来会误解"的地方，都要处理，不能留着当历史包袱。**

包括但不限于：
- **命名历史遗留**：字段/指标/参数的名字与实际用途不符
  （例：判定早已改用 `gmean_mse`，字段却仍叫 `*_nmse`；
  参数 `active_val_probe_trajs` 实际决定的是 confirm 的条数）；
- **注释与文档过期**：代码/配置注释、技能文档里描述的流程与当前实现不一致；
- **对不上号的口径**：两处名字不同但语义相同（或相反），或同一名字在两张表里含义不同。

处理方式（**三选一，必须明确选一个并说明理由**，不能"知道了但不动"）：
1. **改名**（代价最大、最彻底）：同步改调用方、事件字段、面板、工具、测试；
   若会破坏历史产物可比性 ⇒ 保留旧字段并标注 legacy；
2. **加消歧义注释/别名**（推荐的低成本做法）：在**定义处**写清"名字与用途不符的历史原因
   + 当前真正的语义"，必要时给新名字的只读别名（如 `gmean_mse` 为主、`nmse` 标注 legacy 显示量）；
3. **标注为已知遗留**：写进知识库/技能文档的"已确认冲突"清单，并说明**为什么暂不改**
   （改动面 / 历史可比性 / 影响外部工具）。

**禁止**：只在对话里口头说明、不落盘；或明知会误导却不加注释。
**收尾要求**：每轮改动结束时，检查本轮涉及的文件里是否仍有"读起来会误解"之处，
一并处理或列入待办（写明下次做什么）。

## 阶段 4 · 测试 → 提交 push → 文档与经验

只有**全部改动经用户确认 + 测试通过 + 用户明确表示满意**后才做这一步。

1. **测试**：跑仓库既有测试（先 `--collect-only` 确认可收集，再跑目标子集），把**通过/失败数字**如实报出；
   失败测试要区分"本次改动引入"与"既有失败"（后者给证据，不掩盖）。
2. **提交**：
   - `git commit -F <消息文件>`（**不用 `-m`**：反引号/中文会被 shell 破坏）；
   - commit message 结构：`type(scope): 一句话` + 用户反馈的问题 + 每条改动做了什么 + 验证结果；
   - 提交前 `git status` 核对只包含批准的文件。
3. **push**：单独一条命令，不与大任务串；push 后回报 `旧SHA..新SHA 分支名`。
4. **整理文档与经验**（三处，缺一不可）：
   - **仓库内**：改动说明/设计文档（放在仓库既有文档目录，遵守该仓库的文档组织约定）；
     **同时**把「改动本意」四问（不变量 / 出错症状 / 快速回滚 / 验证入口）落到台账 —— 这是 debug 入口，不是可选项；
   - **agent 记忆知识库**：把可复用的坑与结论写进对应主题文件（改哪里、为什么、实测数据）；
   - **当日工作日志**：记流水（做了什么、实测多少、遗留什么）。
5. 收尾给用户一张**对账表**：改动编号 ↔ 文件 ↔ 验证方式 ↔ 结果。

## 常见坑（本流程实战踩出来的）

- **别把"用户同意的那一步"扩权**：只做被批准的那一条。
- **配置类改动要验证"真的生效"**，不能只看命令里写了：查进程环境（`/proc/<pid>/environ`）或日志里的策略行，否则会出现"写了参数但程序仍用默认值"。
- **锚点用谓词不用行号**：`grep` 到函数名/唯一字符串再改，行号在重构后会全错。
- **shell 里别写复杂引号/heredoc**：脚本写本地 → `scp` → 远端执行（本会话 heredoc 引号踩坑 6 次以上）。
- **回复排版：表格单元格里绝不放多行/代码块**（2026-10-12 用户第三次指出"输出格式有问题"）——单元格不能含换行，塞代码块必然把表格渲染崩。代码一律放表格外，用"改哪里（表格）→ 改前/改后（代码块）"两段式；嵌套清单/多行说明同理移出表格。
- **长任务后台发起**（`setsid nohup … > log 2>&1 < /dev/null &`），读结果另起一次调用；**不等待**。
- **撤回要留证**：撤回后必须复跑同一条验证，证明回到改动前状态。
- **提交前跑测试**：带失败测试提交过一次，后面花更多时间补修。
- **🔴 并行/分片类改动：先问"这个分支该不该管单卡"**（2026-10-12 实战踩坑）：
  为多卡写的优化（按卡切分、锁死每卡次数）**必须显式门槛**（`if world > 1`），
  否则会**悄悄改掉单卡路径的行为/测量口径**——本次实测：单卡扫描的"每 50 帧一个窗口"
  被改成"每条轨迹摊 2 个窗口" ⇒ 同一轨迹 MSE 差 0.5–4.7 倍、43/50 任务与历史不一致，
  而**程序不报错**。判据：任何"按设备数/并行度"分支，都要有"单卡回归"验证
  （重跑一遍与历史基准对比，逐项相对差 <5%）。
- **🔴 共享文件名必须带"内容指纹"**：多进程写同一个文件时，
  "内容相同 ⇒ 谁赢都一样"只在**输入相同**时成立；分片/扫描等**各卡输入不同**的场景，
  文件名要区分（`<tag>_<指纹>.json`），否则会出现"不报错但结果来自别人的数据"。
  本次实测：`rank2 run_ids=[1408]` 却返回 `per_traj_ids=[1403]`（花了 6 轮真机运行才定位）。
- **🔴 定位"数据对不上"类 bug 的有效顺序**（本次总结，省轮次）：
  ① 在**关键汇合点**打一行"输入/输出原样值"（不是摘要）；② 用"各卡是否不同"作为判据；
  ③ **一条评测成功、下一条失败**这种模式 ⇒ 优先怀疑"第一次遗留的全局状态/共享文件"；
  ④ 每次只改一处、只跑一轮，别同时改多处（否则无法归因）。

### 🔴 2026-10-13 新增（5 条，都是本会话真金白银踩出来的）

- **🔴🔴 验证必须覆盖"真正会出问题的那条路径"，不能只验顺路的那条**（本次最贵的错）：
  我为"`final_only` + 周期存 HF"做的验证用的是 `--steps 10`（从 `step_offset=2400` 起），
  结果它**立刻满足收尾条件** ⇒ 走的是**收尾存档**路径（那条会写 DCP，所以 HF 转换能成功），
  而**周期存档**路径（不写 DCP）**一次都没被验证**；正式跑起来就在周期边界崩了
  （`assert metadata is not None`），44 分钟训练 + 池子全丢。
  ⇒ 判据：**先说清"这份产物由哪条分支产生"，再设计能走到那条分支的参数**
  （本例：`--steps > offset + N` 才会进入周期分支）；**只验一次成功 ≠ 该组合可用**。
- **🔴 参数的选择有"硬校验"，不满足会启动即崩 —— 传参前先读校验代码**：
  本次两次栽在同一处：`hf_pass_interval`（脚本默认 **2**）与 `save_hf_weights=true` **互斥**
  ⇒ `ValueError: hf_pass_interval 需要 … save_hf_weights=false …` ⇒ 进程 0 秒退出。
  ⇒ 规矩：新参数组合先在 `grep -n "raise ValueError" <入口文件>` 里核对一遍前置条件，
  **别用"上次那次恰好能跑"推断这次也能跑**（上次能跑往往是因为"恰好传了某个值"）。
- **🔴 停机/存档前先跑一次"容量预判"，不要用记忆里的体积数字**：
  我凭技能里的旧实测（"DCP ≈24 G"）判断 56 G 可用空间够，于是让用户停机；
  实际该配置的收尾 DCP 预判值是 **≈72 G** ⇒ **收尾存档被容量闸门跳过** ⇒
  **训练停了、什么也没存下**（池子也随进程消失）。
  ⇒ 规矩：停机前**读一次闸门自身的判据**（本项目 `_dcp_final_capacity_ok()` 的预估值会打进日志），
  并把**输出目录放到大容量盘**；容量结论要引用"闸门怎么算"，不是"我记得多大"。
- **🔴 步号有两套以上，报数必须带口径**：本项目同时存在
  **全局步**（`Step: 4050`、`global_step_4050`）、**子系统内部步**（事件流 `step`，`tb_step` 才是全局）、
  **unit 数**。面板"历史"行用的是**内部步** ⇒ 与用户对不上（用户据此问"早就过线怎么还在学"）。
  ⇒ 规矩：报告/文档里**写明口径**，能用全局步就用全局步；事件流里 `step` 与 `tb_step` 并存时**取后者**。
- **🔴 别用 `echo/grep` 把要匹配的模式串写进同一条命令**（自匹配假警报）：
  `grep -acE "Traceback|AssertionError" $LOG` 前若有一条 `echo "… Traceback|AssertionError …"`，
  计数会把**自己那行**算进去 ⇒ 实测报出"7 个报错"其实**全是噪音**（真值 0）。
  ⇒ 规矩：计数类判断用**脚本文件**（本地写 → scp → 执行）或至少把模式串放进变量，
  **并在结论前用第二种方式复核一次**（本次改用 Python 正则重数 ⇒ 0）。
