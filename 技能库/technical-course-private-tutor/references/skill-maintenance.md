# Skill 更新、博客化与外部知识资产原则

> **来源**：Skill 更新、博客化与外部知识资产原则 — https://www.cnblogs.com/yong2333/articles/22998468
> **类型**：blog ｜ **主题**：skill-maintenance
> **作用**：本 skill 的自我更新方法论；也适用于任何"长期演进的 Agent Skill"。

## 核心原则

Skill 的更新目标，**不是记住某一次任务是怎样完成的**，而是从实际使用、修改和反馈中，持续提炼可以跨任务复用的判断方法。

> Skill 应越来越会判断，而不是越来越像一个堆满具体案例、固定答案和一次性要求的仓库。
>
> 同时，Skill 不需要把所有知识都写进自身正文。对于文章、博客、论文、文档、网站、GitHub、官方资料等外部信息，应尽可能保留其原始来源链接，使 Skill 在需要时能够重新访问原始资料，而不是依赖经过压缩后的二手记忆。

## 一、Skill 更新原则

### 1. 从具体反馈中提炼通用规则

收到一次修改以后，不直接把用户原话加入 Skill。先判断这个问题属于：局部修改 / 当前任务规则 / 通用规则。

只有**通用规则**才进入 Skill 的长期规则体系。判断标准是：**换一个主题、换一篇文章、换一个任务，这条规则是否依然成立？** 如果不能，就不应成为永久 Skill 规则。

### 2. 新规则必须通过通用性测试

一条规则准备进入 Skill 前，至少检查：

- 是否与当前具体主题无关；
- 是否可以应用于多种不同任务；
- 是否解决一种可重复出现的失败模式；
- 是否能够明确执行；
- 是否能够在最终检查中发现；
- 是否不会过度限制其他任务；
- 是否已经被现有规则覆盖。

Skill 保存的是**为什么这样处理更好**，而不是**上一次具体是怎么改的**。

### 3. 反馈先抽象，再全文扫描

用户指出一个问题以后，不应该只修改被指出的位置。采用：

```
具体反馈 → 判断问题类型 → 抽象出问题机制 → 检查全文是否存在同类问题
        → 批量修正 → 检查旧反馈有没有被重新引入
```

一次局部反馈，有时暴露的是一个系统性问题。

### 4. 旧规则默认保留

更新 Skill 时，旧版本中的规则默认全部保留。**更新前建立旧规则清单**，更新后逐项确认：保留 / 合并 / 改写 / 拆分 / 建议删除。

不能因为重新组织 Skill，就让旧规则静默消失。**重写不等于重新发明。**

### 5. 优先合并，而不是不断增加规则

遇到新经验时优先判断：能否加入已有规则？能否扩展已有检查项？是否真的需要成为独立规则？

如果两个规则解决的是同一个问题，应尽可能整合。但规则合并以后，必须确认旧规则原来防止的失败模式仍然全部被覆盖。

### 6. 新旧规则发生冲突时，不擅自决定

如果出现下列情况，则不能由 Skill 自行决定：

- 新规则与旧规则方向相反；
- 两条规则无法同时满足；
- 合并会改变原规则含义；
- 要把"建议"升级为"必须"；
- 要把"默认行为"改成"禁止行为"；
- 会明显改变整个 Skill 的风格。

应该明确列出：**旧规则是什么 → 新经验是什么 → 冲突在哪里 → 可以怎样处理**。最终规则方向由用户决定。

### 7. 每条规则都必须对应一个失败模式

新增规则时必须能够回答：**这条规则到底是在防止什么问题？**

例如：信息没有来源；用户修改后旧错误重新出现；长文变成 PPT；标题没有信息量；搜索很多但主线越来越散；模型把一次性的要求误当成永久规则。

不能仅仅为了让 Skill 看起来"更完整"而添加规则。

### 8. Skill 保存判断方法，而不是固定模板

优先写「在什么情况下应该怎样判断」，而不是「永远必须这样做」。

具体案例和示例只用于解释规则，**不自动成为模板**。案例中的人物、行业、数字、网站、表达方式和结构，都不具有永久约束力。

## 二、Skill 与博客之间的转换原则

### 9. Skill 应能够直接生成博客

一个成熟的 Skill 不应该只是内部提示词或操作规则。它应该能够把自身积累的方法、研究过程、案例、判断和知识整理为一篇可以直接阅读和发布的博客文章。

因此 Skill 应具备两种输出形态：

| 形态 | 面向 | 内容 |
|---|---|---|
| **执行形态** | 指导 AI 完成任务 | 判断规则、工作流、检查项、决策条件、异常处理 |
| **博客形态** | 向人解释 | 为什么产生这些规则、解决了什么问题、实际遇到了什么失败、为什么后来修改、当前得到什么方法、还有哪些问题没解决 |

> 也就是说：**Skill 是可执行的方法，Blog 是可阅读的方法。** 二者来自同一知识体系，但表达方式不同。

## 三、Skill 不必吞掉所有参考资料

### 10. 区分"规则资产"和"知识资产"

**A. 规则资产** — 真正进入 Skill 主体的内容：判断原则、工作流程、通用方法、检查机制、失败模式、决策条件。应高度抽象、稳定、可迁移。

**B. 知识资产** — 不需要完整写进 Skill，但应该保存：参考博客、官方文档、论文、GitHub 仓库、数据页面、新闻报道、视频、PDF、社区讨论、搜索结果、其他参考文件。

> 知识资产的重点不是"背下来"，而是：**保留找到原始信息的路径。**

## 四、外部来源优先保存链接

### 11. 来源博客和参考资料可以只保存 URL

对于可以稳定访问的外部资料，不需要把全文复制进 Skill。可以保存：**名称 + URL + 简短说明 + 它支持什么问题**。

这样可以避免 Skill 因复制大量资料而越来越庞大。

### 12. 链接不是注释，而是外部知识入口

保存来源链接的目的，不只是告诉读者"这句话有出处"，还应该让 Skill 能够：

```
发现需要某项知识 → 找到对应来源 → 打开原始链接 → 阅读最新原文
→ 提取当前任务需要的信息 → 回到任务继续工作
```

因此 **URL 本身属于 Skill 的知识资产**。

### 13. 优先访问原始来源，而不是依赖旧摘要

如果 Skill 中同时存在「以前生成的摘要」和「原始文章链接」，在需要准确细节时应优先重新访问原始来源。尤其是涉及数字、版本、API、法律、政策、软件文档、持续更新的博客、GitHub、官方说明时，不能假设旧摘要仍然完整或最新。

> 原则是：**摘要用于快速定位，原文用于最终确认。**

## 五、建立 Reference Registry

### 14. Skill 可以维护一个轻量级参考资料索引

不需要把资料全文塞进 Skill。字段见 `reference-registry.md`。

这个索引相当于 Skill 的**外部知识地图**：Skill 本身保存"如何思考"，Reference Registry 保存"去哪里重新找到证据和原始知识"。

## 六、Skill、Reference 与 Blog 的关系

```
外部原始资料
      ↓
Reference Registry
      ↓
研究与实际任务
      ↓
发现问题 / 用户反馈
      ↓
局部经验
      ↓
通用性测试
      ↓
Skill 规则更新
      ↓
新的执行结果
      ↓
新的博客文章
```

同时：

```
Blog → 保留来源链接 → 后续 Skill 可以重新访问 → 获得原始信息 → 继续研究和更新 Skill
```

因此整个体系不是单向的 `资料 → Skill → Blog`，而是：

> **资料 ↔ Skill ↔ Blog ↔ 新资料**

形成一个可以持续积累和重新验证的知识循环。

## 七、最终更新工作流

```
收集新的反馈与经验
→ 区分局部修改 / 当前任务规则 / 通用规则
→ 对候选规则进行跨主题测试
→ 建立旧规则清单
→ 检查现有规则能否覆盖
→ 优先扩展或合并旧规则
→ 检查是否造成旧规则丢失
→ 新旧冲突交给用户决定
→ 更新 Skill
→ 更新版本差异
→ 收集本次任务产生的高价值外部来源
→ 将来源 URL 写入 Reference Registry
→ 必要时从 Skill 生成可直接发布的 Blog
→ Blog 保留关键来源链接
→ 后续任务需要时重新访问原始来源
```

## 最核心的三层结构

| 层 | 保存什么 |
|---|---|
| **Skill** | 方法、规则、判断能力 |
| **Reference** | 原始来源在哪里 |
| **Blog** | 一次完整思考是如何发生的 |

三者不要互相替代。

> 最理想的状态不是让 Skill 自己变成一个越来越大的知识库，而是：
> **Skill 越来越聪明，Reference 越来越完整，Blog 越来越能记录思考过程。**
> 这样即使 Skill 本身保持精简，也可以在需要的时候沿着链接重新访问原始资料，恢复完整上下文，并继续产生新的知识。
